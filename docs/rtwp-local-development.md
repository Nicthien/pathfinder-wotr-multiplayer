# Local RTwP variant

This tree is an experimental, local-only derivative of multiplayer 0.4.16. It must not replace the stable installation until the real-time protocol and in-game synchronization are validated on two machines.

## Safety invariants

- `00_WOTRMultiplayer` is the stable slot.
- `00_WOTRMultiplayerRTwP` is the experimental slot.
- Only one slot may be enabled at a time.
- Never copy a Debug build into the stable slot.
- Never save while a mode-switch or repair barrier is active.
- The host is authoritative for combat state and random outcomes.
- A failed repair falls back to turn-based combat.

## Local commands

```powershell
.\tools\rtwp-local.ps1 -Action Build
.\tools\rtwp-local.ps1 -Action Status
.\tools\rtwp-local.ps1 -Action StageTest -AllowUnvalidatedTest
.\tools\rtwp-local.ps1 -Action EnableTestExperimental -AllowUnvalidatedTest
.\tools\rtwp-local.ps1 -Action Install
.\tools\rtwp-local.ps1 -Action EnableExperimental
.\tools\rtwp-local.ps1 -Action EnableStable
.\tools\rtwp-local.ps1 -Action CollectDiagnostics -SavePath 'C:\chemin\vers\une-sauvegarde.zks'
```

`Install` creates a timestamped backup of an existing experimental installation and stages it outside the game's `Mods` folder when the stable mod is active. Unity Mod Manager loads any mod folder inside `Mods`, even if its name ends in `.disabled`; inactive slots therefore live in `local-artifacts/mod-slots`. The script migrates older `.disabled` folders out of `Mods` with the game closed, checks the game directory and all source/destination slots before moving a mod, and refuses changes while `Wrath.exe` is running. Normal installation and activation remain locked until a local `local-artifacts/RTWP_RUNTIME_VALIDATED.json` records protocol version 25 and a successful two-instance combat test. For development only, `StageTest` stages an unvalidated build outside `Mods`; `EnableTestExperimental` requires the explicit `-AllowUnvalidatedTest` flag and switches away from the stable mod. Run such tests on a copy of a save, then use `EnableStable`. Neither action creates the validation marker. `Build` does not touch either installed mod.

`CollectDiagnostics` copies only the current local game logs into a timestamped directory under `local-artifacts/diagnostics` and records active/disabled mod identities. The optional `-SavePath` records a SHA-256 hash but never copies or edits the save. No data is uploaded. Logs can contain local paths, player names and IP addresses, so review them before sharing. This action is read-only with respect to the game and may be run while it is open.

## Current milestone

The first milestone provides the deterministic state machine for mode-switch barriers, epoch/sequence rejection, three pause policies, a canonical snapshot fingerprint, repair attempts and automatic turn-based fallback. A matching game/mod/DLC/protocol check prevents starting an incompatible lobby. Protocol version 14 adds host-to-client combat snapshots, client hash replies (including explicit application failures), host-validated move/attack/ability command messages, synchronized manual pause requests, a Prepare/Ack/Commit/Ack/Complete/Ack mode-switch transport, a paused Verify/Apply/Resume/Ack repair path with turn-based fallback after two failed applications, epoch-numbered host AI choices, a synchronized preferred combat mode and application-level snapshot response telemetry. Incoming commands are executed on the host's main thread before acknowledgement, and the client only advances its command sequence after local application. The in-game Escape menu's multiplayer lobby now shows the combat phase, preferred mode and pause policy and gives the host mode, preference, policy and manual-repair controls; both players see pause/resume controls. A preference mismatch is applied once at the next running combat, while a manual switch wins for the remainder of that combat. These controls compile and refresh from synchronized state, but their layout and behavior have not been visually tested in the running game. Initial client-side interception of player movement, attack and ability commands and host-originated order broadcast are present, but have not been exercised in game; unsupported commands are blocked in the experimental real-time path. A game save is denied during an active synchronization or repair barrier. The moving-snapshot hash covers projected combat state and the last 32 accepted host orders, but not the live command lifecycle or authoritative random stream. Client AI selection now waits for the host's choice, but rule-result authority and projectiles are not yet complete. The displayed response time includes client processing; missing application replies are not a measure of underlying TCP packet loss. All protocol and repair paths still need two-instance game validation; the stable turn-based runtime remains the only supported in-game mode. Do not create the validation marker merely to bypass this lock.

The local variant includes a complete `frFR` pack matching all 211 current English keys and placeholders. The build checks it before compiling. The two known local voice mods (`WOTR_AIVO` and `SpeechMod`) may differ between players; all other gameplay mods remain subject to strict version matching. A read-only inspection of the installed `WOTR_AIVO` 0.2.0 binary on 2026-10-01 found that its dialogue playback hooks run after `LocalizedString.PlayVoiceOver` and `PlayCueVoiceOver`, while multiplayer synchronizes dialogue through `DialogController.StartDialog` and cue/answer hooks; no matching audio-hook target was found in the multiplayer source. This is only static compatibility evidence, not proof that voice playback works in-game. See `docs/session-2026-09-30-diagnostics.md` for the outstanding voice check.

Snapshot failures now produce an explicit failed-application reply. When the state can be read but its fingerprint differs, the client includes a bounded list of differing unit and area-effect IDs in its reply; the host logs that list before starting paused verification. If even the turn-based fallback checkpoint cannot be applied, both sides remain paused and saving remains blocked. This is a safety stop, not a complete host-state reconstruction. Missing summons or area effects still require a fuller reconstruction mechanism before a campaign-ready release. The locale packs now also cover the new combat controls; their key count is greater than the original 189-key baseline.

Until rules, random streams, summons and effects are fully authoritative and reconstructable, saves are refused throughout an active real-time combat, even when its latest checkpoint matches. Switching safely to turn-based or ending combat permits the normal synchronized save path. This conservative restriction prevents a save from capturing a divergence during the interval between snapshots.

The mode and repair barriers now retransmit their current message twice before counting a timeout as a failed attempt. Duplicate Prepare and Commit messages are acknowledged idempotently on the client, while a full Abort or Fallback checkpoint can recover a client that missed Prepare entirely. This improves behavior under dropped/reordered application messages, but is not a substitute for a two-instance fault-injection run in the game.

Mode completion now has its own acknowledgement. The host remains paused with saving blocked until every connected client acknowledges the final Complete message; if it is missed, the host retransmits it without aborting into a potentially conflicting mode. If the peer disconnects during this last barrier, the host can finish in solo play. Both successful commits and rollback completions use this last barrier.
Moving combat snapshots and accepted player commands are ignored by a client while a mode-switch, repair or fallback barrier is active, even if their epoch and sequence are otherwise current. Only stable RTwP combat accepts them.

Repair completion likewise holds the host paused and blocks saving until each connected client acknowledges Resume. A lost Resume is retransmitted, and a duplicate is acknowledged by a client that has already resumed. This applies to both a repaired RTwP state and the turn-based fallback.

Before applying any RTwP checkpoint, the client now verifies that every referenced unit and area-effect entity exists locally. If a summon or effect is absent, no partial checkpoint is applied; the failure reply includes bounded entity IDs and the host enters paused repair. This improves diagnosis and safety, but does not yet create the missing entity; a repeatedly missing entity still causes the protected turn-based fallback stop.

The preflight also validates units referenced inside active areas and by combat engagements. A missing area occupant or engagement target is rejected before any unit, buff or area mutation, with a bounded cause such as `missing-area-unit:cloud:summon` or `missing-engagement-target:hero:enemy`.

The paused checkpoint preflight also rejects duplicate unit/area IDs and non-finite positions or orientation before applying any mutation. Divergence diagnostics now name differences in projected position, damage, buffs and area occupants, and report duplicate IDs or invalid coordinates without the diagnostic itself throwing. This is a safety and observability improvement, not missing-entity reconstruction.
It rejects incomplete positional, health/state, buff and area payloads before mutation as well. Scripted allies without a combat-state component are allowed, and the checkpoint updater skips engagement changes for them instead of dereferencing a null component.
Non-lethal damage is now projected from the game's character stats into each combat checkpoint and restored on the client. A missing stats payload is rejected by RTwP preflight before mutation; the legacy turn-based updater tolerates it. The moving fingerprint already covered this field, and a test now confirms that non-lethal damage changes the fingerprint. This is a code-level check, not an in-game validation of unconsciousness or recovery.
The checkpoint projection now carries the host's `NotSurprised` combat flag instead of always sending its default value. Position correction tolerates a scripted ally without a combat-state component. RTwP preflight rejects null buff entries and incomplete engagement collections before mutating any unit; these checks have unit coverage but still require in-game verification.
An area-effect entity without a loaded view is now rejected before applying a checkpoint, rather than silently skipped after other entities were mutated. A unit without a view can still receive its logical position without dereferencing that view. These cases need real-game coverage, especially around scene transitions.

The moving fingerprint now also contains a bounded ledger of the last 32 orders accepted by the host, including a digest of each move/attack/ability payload. The client records an order only after successfully executing the host's accepted message. This detects missing or altered command traffic; it is not yet a complete projection of all currently executing Unity commands.

Protocol version 15 additionally fingerprints prone state and both sides of unit engagement, so a knockdown or attack-of-opportunity relationship mismatch enters the same repair path. Engagement collections are sorted canonically before hashing. Elapsed engagement rounds are deliberately omitted from the moving hash because the game derives them from local game time and host/client snapshot reads are not simultaneous.
Protocol version 16 sends each unit and area-effect blueprint ID, fingerprints it and rejects a checkpoint if an existing local entity has a different blueprint. The bounded divergence report names blueprint mismatches. These IDs are necessary reconstruction metadata, but not sufficient to recreate a summon or an area effect: the game also needs the spawning context, ownership and effect lifetime. No entity is spawned from a bare blueprint ID, and an absent entity still takes the protected repair/fallback path.
Protocol version 17 additionally carries the area-effect caster, owner and source-ability blueprint IDs. They are part of the moving fingerprint, and a mismatch is labelled `area:<id>:context`. This identifies a wrong origin rather than treating every same-blueprint zone as interchangeable. Lifetime and mechanics-context serialization, safe creation, rollback and real-game validation remain open; this metadata alone does not authorize reconstructing an effect.
Protocol version 18 carries unit origin metadata (original blueprint, caster, source ability, master and group) and the area effect's stored creation time and duration. The stable unit metadata joins the moving fingerprint and is labelled `unit:<id>:origin` on mismatch. Area lifetime metadata is available for future paused repair but intentionally excluded from the moving fingerprint to avoid comparing unsynchronized local clocks. No missing game entity is created by this change.
Protocol version 19 makes dice results from the mod's synchronized rule-roll processor host-authoritative in RTwP. Host results are keyed by deterministic rule identity, dice formula, sequence and combat epoch, sent immediately and buffered on the client even if reordered. The client advances its local seeded generator but applies the host result. If the result has not arrived after a bounded 2.5-second wait, the client reports a roll fault and the host enters a paused barrier, then goes directly to the protected turn-based fallback; a local result is used only for that failed in-flight calculation and RTwP is not resumed from it. Protocol version 20 also treats a client-local roll that differs from the host's as a fault: the in-flight rule applies the host result, then both peers enter the protected turn-based fallback. Saving remains prohibited until both peers verify the fallback. These paths have pure mailbox, wire and two-actor protocol tests, including completion of the fallback on both peers, but no game-runtime validation. Other game randomness intercepted outside `MultiplayerRollProcessor`, rule side effects, projectiles and missing-entity reconstruction are not yet fully host-authoritative; this is not campaign-ready.

Protocol version 21 routes the existing confusion and mechanics-context dice patches and mirror-image absorption count through the same host-authoritative roll channel during stable RTwP combat. Their pre-existing local deterministic path is unchanged outside RTwP and during synchronization barriers. Other patched randomness was still local at that version.

Protocol version 22 sends the final two-dimensional miss-scatter point of a projectile through the host-authoritative integer outcome channel, at millimetre precision. The client still advances its local deterministic generators, and a significant local/host difference takes the protected turn-based fallback. The prior exact local point is preserved outside stable RTwP. This covers the existing miss-scatter patch, not projectile lifecycle, collisions or all projectile effects; those remain unverified in-game.

Protocol version 23 sends the selected three-dimensional fear-movement destination from the host, at millimetre precision, rather than relying only on both peers choosing the same index in their local point lists. The local random selection still advances its generator; a destination mismatch requests the protected fallback. The old path remains unchanged outside stable RTwP. No real-game fear movement has yet been validated.

Protocol version 24 carries the owning scene name for each combat unit and area effect. The moving fingerprint and divergence report now include that scene, and paused preflight refuses to mutate a local entity whose scene differs from the host checkpoint. The scene is necessary for future reconstruction, but does not provide the missing mechanics context or unit spawning data by itself.

Protocol version 25 adds a separate temporal integrity check for buff remaining/next-tick/resource times and area creation/duration. The moving fingerprint still excludes these clocks to avoid false per-frame divergence from network transit; the client reports deviations greater than one second after applying a snapshot, and the paused repair Verify stage carries the host checkpoint so it can request Apply even when the structural hash matches. This detects timer drift but cannot yet recreate missing areas or arbitrary buffs.

On 2026-10-01, a local hidden-window startup smoke of the protocol-22 experimental build reached Unity Mod Manager's successful load (445 Harmony-patched methods), French locale initialization and multiplayer window initialization in `Player.log`. The launched game process exited normally after a close-window request, and `EnableStable` restored the installed 0.4.16 slot. This smoke did not load a save, run combat or validate two-instance RTwP behavior. Network-connection errors from the game's external services appeared in the log and are not evidence of a multiplayer-session failure.
When a checkpoint still differs, the bounded unit diagnostic now labels prone and engagement causes where applicable instead of reporting only the unit ID.

The local test suite now also connects host and client protocol actors through an in-memory queued transport. It deliberately drops and duplicates mode-switch messages and drops a repair Prepare, then asserts both peers return to the same stable mode and epoch. A projected-unit mismatch is also tested with a mocked game service that successfully applies the host checkpoint. These are protocol-level two-actor tests, not proof that the real Unity service can reconstruct a missing unit or that combat rules converge under network faults.
The queued transport also injects a moving snapshot and an accepted order while the client is waiting for mode-switch completion; neither mutates client combat state, and the handshake still completes afterward.

The inverse case is tested as well: when the mocked client continues to report a divergent unit after every host checkpoint, both actors remain in the fallback phase with saving blocked. That protects the save, but is explicitly not the campaign-ready recovery path; reconstructing the missing game entity remains open.

Three consecutive snapshot replies aging out (a window of 32 snapshots, normally about eight seconds) now make the host pause and start the same verification barrier. An acknowledged snapshot resets the consecutive counter. This is an application-level liveness guard, not a claim that TCP packets were lost.

On 2026-10-01, a local visible-game smoke of protocol 25 loaded an existing `Prologue_Labyrinth` save with the experimental mod and `WOTR_AIVO` enabled. The multiplayer lobby hosted and started with one player, displayed four owned characters, and its in-game F2 page changed the preferred mode to `Temps réel avec pause` and cycled the pause policy. `Player.log` recorded area loading and both preference broadcasts. No combat or second peer was exercised. The game was closed via its own unsaved-progress confirmation; the source save's SHA-256 still matched a byte-identical backup. The original Unity Mod Manager parameters were restored byte-for-byte and the stable 0.4.16 slot re-enabled. A `CameraRig.OnDisable` null reference appeared while the game was quitting; its attribution is unknown and it did not prevent process exit. This smoke does not satisfy the two-instance combat validation gate.

The host now advances a player's RTwP command sequence only after the game has accepted and executed that command. A failed game execution no longer consumes the sequence, so a retry with the same client sequence can be accepted; duplicate committed commands and old-epoch commits are still rejected. This is covered by command-gate unit tests, not yet by an in-game two-peer test.

If the client disconnects during an RTwP combat or synchronization barrier, a session-local safety latch keeps saving disabled even after its network socket and combat stage disappear. The in-game warning explains that the local state may differ from the host and asks the player to return to the main menu and load a safe save. Closing/resetting the multiplayer game session clears the latch; this avoids locking unrelated later single-player loads. A unit test covers disconnect, combat end and reset. Reconnection and live repair remain unverified.
